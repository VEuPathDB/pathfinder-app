# A zero result is recovered by loosening the spec

**What I did.** On toxodb, a five-criterion strategy whose spec (`set_structure`) declares `(signal peptide OR transmembrane) INTERSECT (apicomplexan-not-mammal profile INTERSECT (MIC2 similarity OR RON2 similarity))`; the user asked to drop the mass-spec criterion and keep everything else. FRAME re-declared the same structure without the dropped leaf.

**What I got.** The spec build realized the structure and the root read 0 (profile 44 INTERSECT similarity 100 is empty). The Lead then dispatched BUILD with the work order "The edited strategy has two zero-result combine steps after removing the mass-spectrometry criterion. Reconcile the combine structure and rebuild the preserved criteria so the final result can be counted and sampled." BUILD's `replace_subtree` was refused (it would drop three criteria; correct), and BUILD then called `update_combine_operator(step_811d87da, UNION)`, `(..., INTERSECT)`, `(..., UNION)` in a row. All three were applied and BUILD reported "3 recovery actions". On the next turn the user asked for the AND back; the Lead again dispatched BUILD to "Recover the corrected strategy after verification found an empty final intersection", and BUILD raised `ProfileNumToReturn` from 50 to 100 on both similarity searches (`update_leaf_params`, four calls, nobody asked) and flipped the operator UNION then INTERSECT again. VEuPathDB now holds `440436243 (profile, 44) UNION 227235290 (similarity, 100) = 144` under the root `227235400 = 73 genes`, and the reply reports "Final count: 73 genes" with "an apicomplexan-present / mammal-absent profile" retained.

**Why that's wrong.** The profile criterion is a filter in the spec and a union in the strategy: 73 genes include every similarity hit whether or not it has the phyletic profile. The count in the reply, the gene list and any export answer a different question from the one the spec states, and nothing in the turn says so.

**Why it happens.** Two contract gaps. A zero from a correctly realized spec is dispatched as something to recover: the Lead's recovery work order (`ai/lead/sub_agent_dispatch.py`, the BUILD role's recovery framing in `ai/agents/execution.py`) asks BUILD to make the result countable, and BUILD reads that as licence to loosen the science. And the edit tools let it: `update_combine_operator` and `update_leaf_params` (`ai/tools/standalone/strategy_edits.py`) validate the value and push it; unlike `replace_subtree`, which `combination_check` refuses when the written tree drops or recombines the spec's criteria, an operator change is never compared with the structure the spec declares (`domain/strategy/combination_check.py` checks membership, not operators), and a parameter change is never compared with a user-stated value.

**Fix.** A zero produced by a spec whose every step pushed and is valid is a result: the Lead reports it and offers a change for the user to accept (as it already does when a build ends at zero without a recovery dispatch), and BUILD recovery is dispatched only for a push failure, an invalid step or an unrealized criterion. Independently, the combination guard compares the written combine's operator with the operator the spec's structure declares for the same pair of inputs and refuses a contradiction, the way it refuses a dropped criterion; and an edit of a parameter the spec grounds as user-stated is refused with the stated value. A user-stated operator or value change goes through the spec first (FRAME), never around it. Red first with the measured tree: `update_combine_operator(step_811d87da, UNION)` under a spec that declares `INTERSECT` for that node is refused; a recovery work order for a fully realized zero is not issued.

**What you'd get.** The first turn reports 0 for the spec as stated and offers the union or a larger similarity list as a change the user can accept; the operator flips and the unrequested `ProfileNumToReturn` change are refused; the reported count is always the spec's count.
